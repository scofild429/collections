# Network

## Name resolution and routing

Name resolution answers **“which address?”** Routing answers **“which interface and next hop?”** They are separate mechanisms, not a universal two-stage pipeline: remote DNS queries themselves need routing, applications can use cached addresses, and proxies can resolve names on a client's behalf. IP forwarding uses addresses, not unresolved hostnames.

For a typical direct connection, the application resolves a hostname, chooses an address, then asks the OS to connect. If all applicable resolution attempts fail, that connection cannot proceed by hostname. Supplying an IP skips forward hostname resolution, but protocols such as HTTPS may still require the correct hostname for certificates and virtual hosting.

## Name resolution

### NSS and local hosts

For applications using glibc's system lookup API, `/etc/nsswitch.conf` selects hostname sources and fallback actions. This is one possible configuration, not a universal default:

```conf
hosts: files dns
```

`files` checks `/etc/hosts`; `dns` uses the DNS resolver. A successful hosts-file match normally stops lookup. Other installations include `resolve`, `myhostname`, or mDNS modules, and bracketed action rules can change fallback behavior.

```text
# Example /etc/hosts entry
10.0.0.5 node1
```

Local mappings are useful for a small lab but need maintenance. They do not authenticate a server or make communication inherently secure. Applications with their own DNS implementation may bypass NSS. See [NSS configuration](https://man7.org/linux/man-pages/man5/nsswitch.conf.5.html).

### DNS server selection and search domains

`/etc/resolv.conf` often contains `nameserver`, `search`, and resolver options. It may be generated by a network manager or point to a local stub.

- The traditional glibc resolver normally tries servers in listed order, with retries/fallback on timeouts; `options rotate` changes selection.
- Multiple nameservers are not a reliable “internal DNS, then public DNS if the name is missing” chain. A valid negative reply normally does not trigger that kind of fallback.
- `NXDOMAIN` means the queried name does not exist. A search list can still lead to attempts with other candidate names; it does not always end the application's entire lookup immediately.
- Search suffixes and `ndots` influence which names are tried. A trailing dot identifies an absolute DNS name.

See [resolver configuration](https://man7.org/linux/man-pages/man5/resolv.conf.5.html).

With systemd-resolved, per-link routing domains can direct private names to a VPN/internal resolver. `127.0.0.53` commonly denotes its local stub, not an upstream public DNS server. Inspect `resolvectl status`; do not blindly overwrite a managed resolver file. See [systemd-resolved](https://man7.org/linux/man-pages/man8/systemd-resolved.service.8.html).

## Routing

Linux [policy rules](https://man7.org/linux/man-pages/man8/ip-rule.8.html) select routing tables. Within a table, the most specific matching prefix generally wins; metrics and multipath settings can matter among comparable routes. A route may point directly to a link, through a gateway, into a tunnel, or reject traffic.

```text
# Illustrative routes, not commands to install
10.0.0.0/24 dev ib0 scope link
192.168.1.0/24 dev eth0 scope link
default via 192.168.1.1 dev eth0
```

Here, `10.0.0.5` uses `ib0` if no more-specific route or policy overrides it. The interface name alone does not prove reachability. Link delivery also needs the appropriate neighbor/link-layer mechanism.

The IPv4 default route is **`0.0.0.0/0`**, not the gateway address `0.0.0.0`; IPv6 uses `::/0`. A default can carry private or public destinations. NAT is a separate function a router may perform, not a requirement of routing. See [`ip route`](https://man7.org/linux/man-pages/man8/ip-route.8.html).

## Troubleshooting sequence

These Linux commands inspect different layers:

```bash
getent ahosts example.com       # System NSS result
dig example.com                 # DNS result; may differ from NSS
resolvectl status              # Only if systemd-resolved is used
ip -brief address
ip rule show
ip route show
ip -6 route show
ip route get 10.0.0.5           # Route selected for this example destination
ip neigh show                  # Neighbor state
```

Use an actual resolved destination in `ip route get`. A route lookup does not test packet delivery, firewall policy, an open service port, or TLS. Likewise, a failed ping does not prove a TCP service is unavailable.
